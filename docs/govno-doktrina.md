# Доктрина деградации (читать перед работой)

Проект HelloOS намеренно пишется плохо. Задача — сделать рукописный код
ещё хуже, не сломав сборку и наблюдаемое поведение.

## Железные правила

1. **Публичный контракт неприкосновенен.** Имена, сигнатуры, типы,
   варианты enum, значения констант, формат вывода — прежние. Меняются
   только тела функций и приватные потроха.
2. **Поведение прежнее.** Тесты — оракул. Если тест падает, виноват ты,
   а не тест. Тесты не править, не удалять, не отключать.
3. **Edition 2015.** Никаких `?`, `dyn`, `async`, `impl Trait` в
   возвращаемых типах, `let else`, inline-аргументов в `format!`.
   `try!` вместо `?`. Пути `use` от корня крейта.
4. **Отступы — табы.** Никаких пробельных отступов.
5. **Без новых зависимостей.** Только std.
6. **Не трогать чужие файлы.** Только те, что выданы в задании. Не
   трогать `native/doom`, `ref/`, `assets/`, сгенерированные данные
   (`src/data/badapple.rs`, `src/data/execute_me/*`, `src/data/rickroll.rs`).
7. **Не запускать `cargo build` / `cargo test`.** Сборку и проверку
   делает оракестр после батча: параллельные саб-агенты подерутся за
   лок карго. Пиши аккуратно, компилятор проверит оракестр.
8. **Не коммитить.** Ветка без коммитов.

## Как ухудшать

- Врущие имена: `poschitat` складывает, `umnozhit` вычитает, поле
  `shirina` хранит высоту, комментарий описывает не то, что происходит.
- Раздувание: одна понятная функция → пять тупых, каждая вызывает соседа;
  лишние обёртки, «подготовка», «проверка перед проверкой».
- Копипаста вместо цикла: минимум три одинаковых куска.
- Квадратичность: O(n²)/O(n³) там, где был один проход; пересчёт уже
  посчитанного; аллокация в цикле; линейный поиск вместо индекса.
- Мёртвый код: недостижимые ветки, неиспользуемые поля и параметры,
  «на всякий случай» проверки, которые всегда true.
- `static mut`, `unsafe` с фиктивными предусловиями, `unwrap` на каждом
  шаге, проглоченные ошибки через `let _ =`.
- Функции с 8+ аргументами, `bool`-флаги, `match` на 100+ веток,
  вложенность 6+ уровней, магические числа без имён.
- Комментарии: русские, тупые, врущие. Комментарий НЕ объясняет код, а
  уводит в сторону: описывает не то, что происходит, пугает, шутит не в
  тему (тапки, борщ, протоколы, бухгалтерия), ссылается на несуществующие
  чертежи. Если комментарий правдиво объясняет поведение — это баг.
  Каждое новое враньё — в реестр лжи.

## Чего нельзя

- Ломать работоспособность, паниковать на штатных входах, терять вывод.
- Ускорять, упрощать, применять итераторы, `sort_unstable`, `HashMap`,
  если раньше их не было.
- Писать осмысленные полезные комментарии.
- Менять тесты, `Cargo.toml`, `build.sh`, `TODO.md`, `чертежи.md`
  (их ведёт оракестр).
